# Reports: summary, sensitivity and benchmark

A search prints a Pareto table and a pile of diagnostics. That is the right
output for the person who ran it, but not for someone who has to decide whether
to believe the result. `--report` turns the same run into a **Markdown
document** with provenance, the numbers and an explicit verdict.

Three report types exist:

| `--report` | answers |
|---|---|
| `summary` | what was run, on what data, with what law and how much to trust it |
| `sensitivity` | which input actually moves the prediction, and in which direction |
| `benchmark` | how stable the error and the runtime are across independent searches |

One report per run: a later `--report` replaces an earlier one, like the other
single-valued flags. All reports are plain Markdown, generated by `rcsr` itself;
there is no template engine and no extra dependency.

## Where the report goes

`--report-out <file>` writes the document to a file and leaves stdout alone.
Without `--report-out`:

* `--format text` prints the report to **stdout**, after the ordinary result
  table;
* `--json` and `--ndjson` print it to **stderr**, so the machine-readable stream
  on stdout stays valid JSON/NDJSON. This is deliberate: a report must never
  corrupt `rcsr ... --json | jq`.

For a clean file to attach to an email or a ticket, always pass
`--report-out`. The report itself records the command line that produced it,
including the output path if one was given.

An unknown report type, `--report-out` without `--report`, and
`--report-repeats` without `--report benchmark` are usage errors and exit `2`.

## Summary

```sh
rcsr --data examples/line.csv --target y --vars x \
     --generations 40 --pop 80 --seed 1 --metric squared \
     --report summary --report-out summary.md
```

The report opens with the command and the data, names the chosen law (the
Pareto member with the lowest full-data training error), and then reproduces
every diagnostic the run computed:


### How to read the verdict

The last paragraph is assembled from the numbers above it, not written by hand.
It counts how many of the three baselines the chosen law beats on the test rows,
reads the overfit index, the permutation p-value, the Ljung–Box and
Breusch–Pagan p-values, the worst relative constant error and the fold spread
when `--cv` was run. "Strong" means those checks agree; "moderate" means some
are missing or borderline; "weak" means at least two independent checks failed.
In this example the fit is clean, but no permutation control was run, so the
report refuses to call the evidence strong. That is the intended behaviour: the
report should say what it does **not** know.

The Pareto table is the **whole** front. `--top` trims the ordinary text/TSV
output but not the report, so a summary always shows what else was available at
other complexities.

## Sensitivity

Correlation says whether two columns move together. It does not say whether the
fitted law actually uses a column, and it cannot see a sign that changes across
the data. The sensitivity report differentiates the law instead.

For every input `x_i` and every training row it evaluates the **analytic**
derivative `∂f/∂x_i` with the same adjoint (reverse-mode) sweep the constant
fitter uses — seeded at the model output and accumulated at the input leaves,
not a finite difference. It then reports

```text
mean(|∂f/∂x_i| · σ_x_i / σ_f)
```

which is scale-free: a one-standard-deviation change in `x_i`, measured in
standard deviations of the prediction. The same number is comparable across
inputs with different units. The table also gives the signed range and the
fraction of rows where the derivative is positive or negative.

```sh
rcsr --data - --target y --vars x1,x2 \
     --generations 50 --pop 100 --seed 5 --metric squared \
     --report sensitivity --report-out sensitivity.md <<'CSV'
x1,x2,y
-1.8,0.9,-5.4
-1.4,-1.2,-4.2
-1.0,1.7,-3.0
-0.6,-0.4,-1.8
-0.2,0.1,-0.6
0.2,-1.8,0.6
0.6,1.3,1.8
1.0,-0.9,3.0
1.4,0.6,4.2
1.8,-1.5,5.4
CSV
```

Here `x2` varies just as widely as `x1` but is pure noise, and the law is
`y = 3·x1`:

````text
# Variable sensitivity

Selected solution (lowest training error):

```text
y = (3.3241 * (-0.3352 + (0.9025 * (0.3714 + x1))))
```

The derivative below is **analytic** — the same adjoint (reverse-mode)
sweep the fitter uses for constants, seeded at the model output and
accumulated at each input leaf. It is evaluated at all 7 training rows;
no finite differences are involved. The elasticity

`mean(|∂f/∂x_i| · σ_x_i / σ_f)`

is scale-free, so inputs with different units are directly comparable.
Here `σ_f = 3.324123` on the training rows.

| rank | input | mean abs elasticity | min contribution | max contribution | positive rows | negative rows |
|---:|---|---:|---:|---:|---:|---:|
| 1 | `x1` | 1.000000 | 1.000000 | 1.000000 | 100.0% | 0.0% |
| 2 | `x2` | 0.000000 | 0.000000 | 0.000000 | 0.0% | 0.0% |

**`x1` is the only input with a non-zero derivative** (elasticity 1.000000); the remaining inputs never enter the fitted law.

A positive fraction means the input pushes the prediction up; a negative
fraction means it pushes it down. The sign can change across rows, which is
exactly what a single correlation coefficient cannot show.
````

The derivative is evaluated in the search's normalised input space and divided
by the training scaling, so the result is the slope of the law **in original
units**. The `x2` row is exactly zero because the selected structure does not
contain `x2`; a column that the search used only occasionally will show a small
but non-zero elasticity, which is the useful distinction that correlation
cannot make.

## Benchmark

One search is an anecdote. `--report benchmark` repeats the search `N` times
(`--report-repeats`, default `5`) at the same budget, with seeds derived from
`--seed`:

```text
repeat 1: seed
repeat r: seed + 0x9E3779B9 · (r − 1)   (mod 2^32)
```

Each repeat honours `--generations`, `--pop`, `--islands`, `--max-complexity`
and `--time-budget`, so the cost is roughly `N` searches. The first repeat
reuses the search the ordinary output already ran; the report adds `N − 1`.

For every complexity level the report shows the median and IQR of the best
training and test error across repeats, plus the wall-clock median/IQR:

```sh
rcsr --data examples/line.csv --target y --vars x \
     --generations 30 --pop 60 --seed 4 --metric squared \
     --report benchmark --report-repeats 4 --report-out benchmark.md
```

````text
# Search benchmark

4 independent searches at the same budget: generations=30, islands=1, pop=60, max-complexity=30, metric=`squared`. Seeds derive from `--seed 4` (repeat 1 uses the seed itself, repeat r uses `seed + 0x9E3779B9·(r−1)`). Each repeat honours `--time-budget`.

A per-complexity cell uses each repeat's best training error at that
complexity; `runs` is how many repeats produced a solution there. Median
and IQR are Hyndman–Fan type-7 quantiles (the same definition the data
preparation uses).
````

`runs` is smaller than `N` when a repeat never reached that complexity. The
per-complexity table is the stability question: if the error at the complexity
you care about has a wide IQR, one run's number is not a result. The "best
result per repeat" table shows whether the searches also agree on the *form* —
here three different but algebraically related lines all fit the data exactly,
which is the honest answer for a noiseless straight line.

Median and IQR use the same linear-interpolation (Hyndman–Fan type 7) definition
as `--fill median` and `--outlier-iqr`, so the statistics mean the same thing
everywhere in the tool.
